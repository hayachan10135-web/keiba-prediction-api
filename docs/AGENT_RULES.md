# プロジェクト運用ルール

## 1. backend-render（Python API）修正時の自動デプロイルール
- `backend-render` 配下のコード（`main.py` など）の修正・追加・削除タスクを完了した際は、明示的な指示がなくても **必ず以下のGit操作を自動実行して完了すること**。
  1. 構文エラー（SyntaxError）等がないかセルフチェックする。
  2. ターミナルで `backend-render` ディレクトリに移動する。
  3. `git add .` を実行する。
  4. 修正内容を端的に表すコミットメッセージ（例: `fix: ...`, `feat: ...`）で `git commit` を行う。
  5. `git push origin main` を実行して、Renderへの自動デプロイをトリガーする。
  6. プッシュ完了とコミットハッシュをユーザーに報告してタスクを終了する。

## 2. android-app / colab-notebooks 修正時のルール
- `android-app` や `colab-notebooks` の修正時は、ユーザーが明示的にGitコミットやプッシュを求めた場合を除き、プッシュは行わないこと（ローカルでのファイル保存・修正のみで完了とする）。

## 3. baselines/ 配下のベースライン保護ルール
- `baselines/DualHybrid_ConservativeLeverage`（第1世代）
- `baselines/DynamicPercentile_Top5Leverage`（第2世代）
- `baselines/ThreeTier_VirtualAndReal_Cascade`（第3世代: リアル勝負141% ＋ 各場3R仮想観戦保証 ＋ 見送り資金保全）
上記 `baselines/` 配下のファイル（モデル・エンジン・実績データ等）は、確定した実証実績を記録した**公式ベースライン**です。
- 今後の実験や新規開発において、`baselines/` 配下のファイルを直接編集・上書きすることは固く禁止します。新たな実験・改善を行う場合は、必ず別ディレクトリ（例: `experiments/`）で作業すること。

## 4. 未来情報混入防止・ゼロリーク保証ルール (Zero-Leakage Protocol)
バックテストおよび本番推論において、レース当日および未来の情報が特徴量に混入するルックアヘッド・バイアス（先読みの罠）を100%防止するため、以下の具体的手段を義務付けます。

### ① 前日以前の確定データ限定の原則（同日レース間リークの完全排除）
- 騎手・調教師・血統等の集計特徴量（勝率・複勝率・コース別実績など）を算出する際、**レース当日（同日の早い時間帯のレースを含む）および未来の日付のデータを1件たりとも含めてはならない**。
- **具体的実装手段**:
  日付・グループ単位で日次集計を行った後、`cumsum() - daily_val` により前日確定値のみを抽出する：
  ```python
  # 正しいゼロリーク集計コード
  daily["prior_count"] = daily.groupby(group)["daily_count"].cumsum() - daily["daily_count"]
  daily["prior_sum"] = daily.groupby(group)["daily_sum"].cumsum() - daily["daily_sum"]
  daily["prior_rate"] = (daily["prior_sum"] + min_samples * default_rate) / (daily["prior_count"] + min_samples)
  ```
  `cumcount()` や単純な `groupby.cumsum()` による同日レース結果の取り込みは禁止。

### ② 静的スナップショット辞書（全期間集計ファイル）の遡及利用の厳禁
- 特定の未来日付（例: 2026-10-12時点）で全期間を一括集計して保存した `stats_dict.json` 等の静的辞書ファイルを、過去日付（8月・9月等）のバックテストや遡及シミュレーションに流用することは**重大な未来情報混入となるため絶対に禁止**する。
- 過去のバックテスト時は、必ず当該レース日の前日時点で計算された動的集計値を用いること。

### ③ 馬個体の過去走シフトにおける日付検証（Strict Date Verification）
- 馬個体の前走データ（前走着順、前走タイム差、前走上がり3F等）を取得する際は、必ず `race_date` でソートした上で `shift(1)` を行い、かつ **`prev_date < current_date`（前走日が当日より過去であること）をマスク検証** すること：
  ```python
  valid_prev_mask = (prev_date < current_date)
  df["prev_time_diff"] = np.where(valid_prev_mask, shifted_time_diff, default_val)
  ```

### ④ 時系列分割（Chronological Split）の遵守
- 機械学習モデルの学習・評価時は、以下の時系列分割を厳格に維持する：
  - **学習用（Train）**: 2015年 〜 2024年
  - **検証用（Validation）**: 2025年
  - **初見テスト・評価用（Test）**: 2026年（通年 / 8〜10月サブセット）
- ランダムシャッフルによるK-Foldクロスバリデーションは、未来のデータで過去を予測するリークを招くため禁止。時系列に沿ったウォークフォワード検証を行うこと。

### ⑤ 実験スクリプト実行前のアサーション検証
- 特徴量生成スクリプト内には、実行時にリークが存在しないことを保証するアサーションを配備すること：
  ```python
  assert (df["prev_race_date"] < df["race_date"]).all(), "エラー: 前走日が当日以降のレコードが存在します（リーク検出）"
  ```

## 5. 個人利用特化・フェイルファスト例外方針 (Fail Fast & Explicit Errors)
本システムは個人専用ツールであり、見栄えを取り繕うためのサイレントなフォールバックやデフォルト値による例外の握りつぶしは厳禁とする。

### ① サイレント・フォールバックの全面禁止
- データの取得失敗、Webスクレイピング失敗、モデル推論異常、スキーマ不整合、データ欠損等が発生した場合、デフォルト値（0.0やダミー文字列「馬1」、空配列など）で正常系を装って処理を継続してはならない。
- 不正なデフォルト値がDB（Supabase予想キャッシュ・収支台帳）やアプリ画面に流れ込むことを防ぐため、即座に例外を発生（Fail Fast）させること。

### ② 例外・エラー詳細の直接出力（画面・ログ出力の義務付け）
- 例外発生時は、スタックトレース、エラークラス名、HTTPステータスコード、原因となったフィールドやパラメータ、APIレスポンスの生メッセージ（`detail` / `errorBody`）を**サーバーログおよびアプリ画面にありのまま出力・表示**すること。
- 「見栄えを良くするためにエラー文を丸める（例: 単なる『取得に失敗しました』など）」ことは行わず、デバッグと原因特定に必要な生のエラー情報を画面に提示すること。

### ③ バックエンドでの詳細エラーレスポンス
- FastAPIの例外ハンドラ（`Exception`, `ResponseValidationError`, `RequestValidationError`）において、エラーの原因・トレースバック・未充足フィールド情報をHTTPレスポンスの `detail` に明示的に格納してクライアントに返却すること。

## 6. 設計・要件定義の正（SSOT: Single Source of Truth）遵守ルール
- 本システムの仕様・アーキテクチャ・データベース設計の最上位の正（正本）は、以下の2つのドキュメントである：
  1. **`REQUIREMENTS_SPECIFICATION.md`**（要件定義書）
  2. **`SYSTEM_ARCHITECTURE.md`**（詳細設計書）
- 実装コード、データベース定義（Supabase）、および各種ドキュメント（`AGENT_RULES.md`, `HANDOVER.md` 等）に仕様の食い違いが発生した場合は、**常にこの2書を正として判断・同期すること**。
- 要件追加や設計変更が発生した場合は、必ずまず上記2書を更新し、整合性を保った上で実装および他ドキュメントの改定を進めること。

## 7. マニュアル実機テスト投票の厳格な集計除外規定 (Zero-Interference Protocol)
- 新要件 `FR-BET-07` に基づき提供されるマニュアル（手動・実機テスト）投票機能において、発注された馬券データは `is_manual_bet=true` で永続化される。
- **【厳格な集計除外規定（FR-SET-05）】**:
  マニュアル投票によるレコードは、AIモデルの実戦成績集計（日次サマリー、累計サマリー、回収率計算、的中率計算）から**物理的・恒久的に完全除外**しなければならない。
- 収支集計クエリや統計ビューを作成・改修する際は、必ず `is_manual_bet = false` または `is_manual_bet IS NOT TRUE`（NULL許容）のフィルタを徹底し、AIの実戦回収率の整合性を一切汚さないこと。

## 8. Android APK ビルド＆自動エクスポート規定
- Android アプリ（`android-app`）のコードを修正・最新化した際は、`./gradlew assembleDebug` でエラーなくビルドが完了することを確認する。
- `app/build.gradle.kts` の `exportApkToDrive` タスクにより、ビルド完了時に自動で `G:\マイドライブ\keiba_data\keiba_ai.apk` へ最新APKが配置・同期される状態を維持すること。
- 手動コピーが必要な場合は、ビルド出力（`android-app/app/build/outputs/apk/debug/app-debug.apk`）を確実に Google Drive 上の対象パスへ上書き配置すること。

## 9. HANDOVER.md の継続的更新ルール
- システムの実装内容、仕様変更、動作検証結果、その後のタスク・ロードマップに変更や進展があった際は、明示的な指示がなくても **必ずプロジェクトルート直下の `HANDOVER.md` を最新状態に同期・更新すること**。
- 常に最新のシステム実装状況、アーキテクチャ、タスク進捗、安全ガイドラインが `HANDOVER.md` を一読するだけで正確に把握できる状態を維持すること。

## 10. 実機・実資金への投票実行前の事前確認義務（Mandatory User Confirmation for Real Bets）
- **AIエージェントによる独断での実機発注の絶対禁止**:
  AIエージェントが開発、デバッグ、テスト、保守作業中に、スクリプト実行やAPI呼び出しを通じて **実際の資金が引き落とされる実機発注（即PAT / UMACAスマートの購入確定・実投票）を執行する際は、必ず事前にユーザーへ明示的な確認を行い、ユーザーの承諾・許可を得てから実行すること**。
- **確認事項**:
  - 対象競馬場・レース番号
  - 券種・買い目・馬番
  - 発注金額（1点あたり金額および合計金額）
  - 実行理由（なぜ実機発注が必要か）
- **模擬発注（Dry-Run）の優先原則**:
  検証や動作確認を行う場合は、可能な限り `dry_run=True`（購入確認画面まで進み確定手前で安全中断）を優先して使用すること。やむを得ず実機発注テストを行う場合も、必ず事前にユーザーへ確認を求めること。
- **本番自律稼働との区別**:
  Renderクラウド上のバックグラウンドスケジューラ（発走5分前の自動発注）は、ユーザーがアプリ設定画面から自動投票モードを明示的に有効化（ON）している場合に自律執行されるが、エージェントが手動・アドホックに実資金を発注することは一切許可されない。
